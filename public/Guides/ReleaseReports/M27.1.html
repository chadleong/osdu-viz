Reading the numbers above "New Schemas" (18) counts 11 new rig-equipment record types, 6 experimental seismic processing-product schemas (version 0.0.0, status DEVELOPMENT), and 1 new reference list (CoilTubingWrapType). "Migration Guides" (10) covers the 5 version upgrades plus 5 reference-data content changes (§6–§7). New schemas have nothing to migrate from. "Breaking Change" (1) is a subset of "Version Upgrades" (5), not a separate count (§2). "New Automated Processes" (4) are the schema data quality checks, the DQ dashboard, the Release Reports index with its fact extractor, and the GitLab Pages publishing pipeline (§4).

At a glance
  • Breaking change Risk 2.0.0 drops the separate Preventions[] list. Prevention and mitigation actions are now both recorded under Mitigations[], and a Risk no longer has to be tied to a planned Wellbore. This affects anything that reads Risk records today. (§2)
  • Fixed A security bug in the schema-building tool. Its download routine was still switching off certificate checks for the whole process. Downloads now use a properly verified, request-scoped connection. No published content was affected. (§5)
  • New capability 11 more rig-equipment types (anchors, boilers, cranes, shakers, mud pits and more) can now be recorded and tracked through EquipmentInventory, each with a full worked example. (§3)
  • New capability The Well Reference Point is now part of Well 1.5.0. This is the fixed, recoverable tie-in point for a well's first survey and plan. (§2)
  • New capability (MVP) 6 experimental seismic processing-product schemas, covering post-stack and pre-stack products, 2D sections and 3D volumes, are open for early feedback. They are at version 0.0.0, so expect changes and do not use them in production yet. (§1)
  • Process change A new Data Definitions portal brings together a Schema Data Quality dashboard and the Release Reports index, and this page is one of those reports. Both rebuild automatically on every master pipeline. (§4)
  • Reference data delivered 6 new reference values: OFFSET and AZIMUTH seismic trace header keys, and the 4-value CoilTubingWrapType list. (§6)
  • Documentation delivered 10 migration guides, plus an expanded Rig Worked Example covering every new equipment type. (§7)
  • Everything else The other 4 version upgrades are purely additive. Nothing already in use is changed or removed.

Technical detail — Geophysics

SeismicTraceData 1.8.0 adds three properties. Contracts[] holds references to applicable agreements in an external contract system of record. AdditionalTraceHeaderRanges[] holds minimum and maximum ranges parsed from trace headers for any parameters beyond the standard set. VelocityModelID is the velocity model used to create the trace dataset.

HeaderKeyName 1.0.0 gets two content-only additions. OFFSET is the distance between energy source and receiver. AZIMUTH is the bearing of the shot–receiver pair, in degrees from North. Both are commonly carried as standard trace header fields in pre-stack data.

Processing products are all osdu:wks:work-product-component--…:0.0.0: SeismicPostStackProcessingProduct, SeismicPostStackTrace2DSection, SeismicPostStackTrace3DVolume, SeismicPreStackProcessingProduct, SeismicPreStackTrace2DSection, SeismicPreStackTrace3DVolume. A processing product groups the sections and volumes produced by one processing project.

Well

Well Reference Point · Risk rework

Wells gain a formal reference point. Risk records are simplified, which is the one breaking change in this release.

Breaking change — FYI for consumers Risk 1.2.0 → 2.0.0 removes the separate Preventions[] list. Prevention and mitigation actions are now both recorded in Mitigations[]. Anything that reads or writes Preventions[] needs updating once this version is adopted.
RecordChangeWhat it does
Risk1.2.0→2.0.0One list of response actions instead of two. Linking to a planned Wellbore is now optional.
Well1.4.0→1.5.0Adds the Well Reference Point, the fixed tie-in point for the well's first survey and plan.
Technical detail — Risk & Well

Risk 2.0.0 makes these changes:

  • data.Preventions[] and all its sub-properties (Name, Description, Status, Responsibles[], ResponsiblesByReferenceIDs[], Deadline, UpdateDate) are removed.
  • data.Mitigations[] is now indexed as nested.
  • data.WellboreID is no longer required.

A schema-upgrade specification (1.2.0 → 2.0.0) is registered so that records can be carried forward.

Well 1.5.0 adds data.WellReferencePoint. The WRP is a permanent, recoverable, fixed point of deepest horizontal constraint, commonly the well's position at seabed or ground level. It records:

  • the WRP type (e.g. Vertical, Slant Rig, Curved Conductor)
  • TVD/MD relative to the well's default vertical measurement
  • inclination and azimuth
  • northing, easting and offset coordinates

Technical detail — rig equipment

Each new type is osdu:wks:master-data--Rig…:1.0.0 with a small set of equipment-specific properties. For example, RigHydrocyclone adds IsMudCleaner, FlowCapacity, AmountOfCones, ConeType and ConeSize.

EquipmentInventory 1.0.0 only let EquipmentID reference RigDerrick or RigPump. In 1.1.0 it can also reference the eleven new types and RigRiser.

The Rig Worked Example now has a full example record for every new type. It also documents RigSurfaceEquipment as planned but not yet published.

Data Definitions Portal & Schema Data Quality

4 new automated processes

This isn't schema content. It's new, published visibility into the state of the schemas and what each release delivers.

New: Data Definitions portal One GitLab Pages portal with three tiles: the Schema Data Quality dashboard, a placeholder Schema Graph Model view (a demo from the in-progress Logical Data Model proof of concept, pending approval), and the Release Reports index, which lists this report. It rebuilds automatically on every master pipeline.
CapabilityWhat it does
Schema data quality checksNewFlags preferred schemas that still reference an out-of-date fragment version, and tracks schema lifecycle status (DEVELOPMENT / PUBLISHED / OBSOLETE) over time.
DQ dashboardNewInteractive dashboard showing the stale-fragment trend, compliance score and status distribution. It regenerates on every check run and every Pages build.
Release ReportsNewOne curated report per milestone, with an index that discovers new reports automatically and a fact extractor that seeds each draft from the change report.
Pages publishing pipelineNewBuilds the whole portal on master only. Pushes to the LDM proof-of-concept branch trigger a rebuild, so the graph model tile stays current.
Technical detail — the DQ toolchain & portal build

SchemaFragmentStalenessChecker.py and SchemaStatusChecker.py are combined by SchemaDataQualityReporter.py and run from OsduApp's new Run schema data quality checks menu item. Each run does four things:

  • scans the preferred schemas once
  • appends a timestamped snapshot to _doc/SchemaDataQuality/DataQualityLog.json
  • refreshes the Markdown trend report with Mermaid charts
  • regenerates a DataQuality:2.0.0-conformant record, LatestDataQuality.json

Generate_DQ_Dashboard.py renders the HTML dashboard from the log. Because the Pages job also invokes it, the local preview file stays gitignored.

PortalBuilder.py assembles the portal page. ReleaseReportIndexBuilder.py builds the newest-first report index. ReleaseReportFactExtractor.py pulls structured facts (schema names and versions, breaking changes, migration-guide counts) out of a ChangeReport.md milestone section to seed the drafting step.

The .gitlab-ci.yml pages job is restricted to master, so a feature-branch push can't overwrite the shared site. A trigger_pages_rebuild job lets pushes to 883-logical-data-models-linkml start a fresh master pipeline.

Schema-Building Tooling

Security · Resiliency · ~28% faster

This isn't schema content either. These are fixes to the internal tool that generates and validates every schema above. A full generation run now takes about 715s instead of about 1,000s, with identical output.

Security fix — already applied The tool's download routine was still turning off certificate verification for the whole process while it fetched reference data. It now uses a verified connection scoped to each request. When a server doesn't send its full certificate chain, the tool recovers the missing intermediate certificate safely instead of skipping the check. No published schema content was affected.
Technical detail — resiliency & performance
  • SSL — Utility.url_retrieve_file() no longer sets ssl._create_default_https_context globally. It uses a request-scoped, verified ssl.SSLContext, and recovers a missing intermediate certificate from the leaf certificate's Authority Information Access extension.
  • Fail fast — an upfront Java availability check means a missing Java runtime is reported before the long generation stages start.
  • Windows file locks — remove_with_retry() and move_with_retry() stop a transient antivirus or indexer lock from aborting a run.
  • Performance — PlantUML diagrams are rendered in batches of up to 100 per JVM launch. The JVM comparisons in BreakingChangeDetection and SchemaUpgradeConfigurationTester run in parallel. Temporary spec-file names were fixed so concurrent migrations no longer collide. New Scripts/Timing.py instrumentation (timings-report.md) makes future regressions visible.
  • Line endings — a repo-wide .gitattributes (* text=auto eol=lf, with explicit binary declarations) handles line endings at commit and checkout. The root cause is also fixed: newline="\n" was added to all 29 text-mode writes across 15 generator scripts. 20 previously CRLF-committed files were renormalised, with line endings only and no content change.
