Reading the numbers above "New Schemas" (24) counts every record type and reference-data list added from scratch this milestone, including the 3 new abstract fragments (AbstractGenericBinGrid, AbstractDefinitiveDepthShift, AbstractUnitEquipment) that other new schemas build on. "Migration Guides" (23) is a different set — it covers the 15 version upgrades plus 8 reference-data changes (§8–§9); new schemas have nothing to migrate from. "Breaking Changes" (3) is a subset of "Version Upgrades" (15), not a separate count (§2, §4).

At a glance — everything below is already approved and shipped
  • Breaking change The Rig data model has been split into 8 focused record types. Heads up for anything reading Rig or Rig Utilization data today. (§2)
  • Breaking change Production reporting records have been restructured to remove ambiguity (e.g. daily vs. monthly, oil vs. water). Heads up for existing production-data consumers. (§4)
  • Fixed A security bug in the schema-building tool — it was silently skipping certificate checks on every download it made, not just the one it was meant to. Closed, no data was exposed. (§7)
  • New capability (MVP) HorizonControlPoints captures the geophysicists / interpreter's original seed picks, with a choice of integrating via RDDMS or working from standalone pointsets. (§1)
  • New capability (MVP) StructureMap carries the gridded surface itself out of the seismic domain and into Earth Modelling, ready to support downstream properties. (§1)
  • New capability (MVP) The new SeismicSurfaceGeneration Activity Template automates the gridding workflow end to end, with full lineage from picks to finished surface. (§1)
  • New capability Rig equipment (derricks, pumps, risers) can now be recorded for the first time. (§2)
  • Process change Building an Activity Template (a workflow definition) no longer needs a schema author. A subject-matter expert fills in a spreadsheet, and the tooling publishes the JSON record, a worked example, a diagram, and the documentation automatically. (§3)
  • Reference data delivered 10 new code lists, adding 117 reference values in total, carried end-to-end through authoring to publication — plus a full refresh of the industry-standard well-log property list (3,909 entries, 16 new). This is the vocabulary work every schema above depends on. (§8)
  • Documentation delivered 23 migration guides — one per changed schema — plus a new authoring guide for building workflow templates, so every change above ships with a consumer-facing explanation. (§9)
  • Everything else The other 12 version upgrades and all reference-data additions are purely additive — nothing already in use is changed or removed.

Well Delivery

Rig rework · Tubulars

The rig data model is split into focused, independently-tracked pieces — the headline breaking change in this release.

Breaking change — FYI for consumers A rig used to be one flat record. It is now the physical rig plus a family of records for its configuration, equipment and utilization — a more accurate model. Anything reading Rig or RigUtilization data will see the new shape once this version is adopted.
RecordChangeWhat it does
Rig1.2.0→2.0.0Now the physical rig only — properties that rarely change.
RigUtilization1.1.0→2.0.0Now only when/where the rig was on location and which hole sections it worked.
RigSpecificationsNewThe rig's configuration during a specific period — the anchor for the four records below.
RigDerrick, RigCirculatingSystemNewDerrick and mud-system details for a given configuration.
AbstractUnitEquipment, EquipmentInventory, RigPump, RigRiserNewTracks equipment fitted to the rig over time, with install/remove/maintenance dates — built on the new abstract equipment fragment.
Technical detail — Rig & Rig Utilization

Rig 2.0.0 — removed OwnerID/TypeRig (→ TypeRigID); added ClassRig, Manufacturer, Model, Generation, service/retire dates.

RigUtilization 2.0.0 — configuration properties moved out to RigSpecifications; added RigSpecificationsID and an AirGaps[] array.

EquipmentInventory — supports RigPump and RigRiser as its first equipment types (more planned); can also attach directly to a Wellbore for rigless operations. All equipment types build on the new AbstractUnitEquipment fragment.

New reference data backing this group: DerrickType, FlareType, GantryType, MooringType (all 1.0.0); RigType 1.0.0 → 1.0.1 (wording only, no value changes).

Domain governance realigned: Rig and its satellites now sit under the Well domain (previously SurfaceFacilities). WellActivity 1.3.0 and WellActivityProgram 1.2.0 updated to reference the new model, including a new Phases[].RigUtilizationID link.

Activity

1 spreadsheet → 4 auto-generated files

The biggest change here isn't a schema — it's how Activity Templates (workflow definitions, e.g. "volume-of-shale calculation") get built. A subject-matter expert fills in a spreadsheet; a new tooling pipeline publishes everything else.

New: proposal-to-production pipeline One spreadsheet in, four published artifacts out, automatically: the ActivityTemplate JSON record, a worked Activity example, a Mermaid diagram, and a markdown reference page. A built-in validation suite and a one-click bulk schema upgrade come with it — authoring a workflow template no longer requires a schema author.
CapabilityWhat it does
4 artifacts per templateNewThe JSON record, a worked Activity example, a Mermaid diagram, and a markdown doc page — all generated from one proposal spreadsheet, every time.
Validation suiteNew3 automatic checks: schema compliance, parameter names matching between template and worked example, and undeclared parameter properties.
Bulk schema-version upgradeNewOne click re-points every template at the latest ActivityTemplate schema version.
Managed-template registryNewProtects hand-authored legacy templates (e.g. ReservoirSimulationRun) from being overwritten by the automation.
ActivityTemplate, AbstractActivityParameter1.1.0→1.2.0Workflow parameters can now carry a human-readable description.
SeismicSurfaceGenerationNewThe first template designed and delivered through the new pipeline, start to finish (see §1).
VolumeOfShaleCalculation-GR1→1.1.0The second template through the pipeline — the automated validation suite caught an error in the existing record, and the fix shipped as a new 1.1.0 version.
Technical detail — the pipeline end-to-end

Fully menu-driven from the Activity Templates menu in OsduSchemaComposer.py: Create Proposal generates a blank workbook pre-filled with template metadata → the author fills in the Parameters sheet (kind, direction, occurrence bounds, optional unit/PWLS property type, and an example value per parameter) → Parse reads every non-Rejected row and writes the four artifacts above → Validate runs the 3-check suite → Refresh Documentation regenerates docs if a JSON record was hand-edited → Upgrade Records to Preferred Schema Version bulk-updates the kind field whenever the ActivityTemplate schema itself moves. A sixth action, Convert JSON Record to Proposal, reverse-engineers an existing record back into a workbook, so authoring a new version never means starting from a blank sheet.

Template versioning follows the same major/minor/patch semantics as schemas: removing or renaming a parameter is major, an additive parameter or unit-quantity fix is minor, wording-only changes are patch.

Templates authored before this pipeline existed — such as ReservoirSimulationRun — are listed in the new _ManagedActivityTemplates.json registry and are explicitly excluded from bulk parsing, documentation refresh, and schema upgrades, so the automation can never clobber a hand-maintained record.

Production

Production Accounting

Production data records are restructured so it's unambiguous what a figure actually represents.

Breaking change — FYI for consumers ProductionValues 1.1.1 → 2.0.0 — previously, period, product and measurement type were independent arrays, so it wasn't always clear whether a record meant, say, daily water production or monthly water injection. The new nested structure ties them together explicitly. Two redundant properties were removed.
Technical detail

Introduces a nested two-block structure so common attributes (ReportingEntityID, StartDateTime, EndDateTime, NominalPeriodID) are defined once and shared. Removed ProductionValuesObservationDescription and ObservationInterval, which overlapped with existing reference data. Backed by an updated Production guide chapter, a new worked example (measured hydrocarbon, daily well allocation, monthly field gas), and a JOLT schema-upgrade resource.

Schema-Building Tooling

Security & reliability

Not schema content — fixes to the internal tool that generates and validates every schema above.

Security fix — already applied The tool's file-download routine had a bug that disabled certificate verification for every download it made, not just the one it was meant to affect — meaning all its internet downloads were briefly unprotected against tampering. Fixed by scoping the change correctly and adding a timeout. No published schema content was affected.
Technical detail — remaining reliability fixes
  • Subprocess hardening — Java calls in the diagram/breaking-change tools no longer run through a shell, now use list-form arguments, timeouts, and upfront existence checks. A tool crash is now a hard error; a completed comparison that finds real breaking changes is not.
  • Error-handling cleanup — silent process exits and bare assertions replaced with proper logged exceptions in three tooling scripts.
  • Two latent bugs fixed during test-suite hardening — one was silently corrupting non-versioned filenames; the other used characters invalid on Windows filesystems.
  • Workbook-naming fix — the reference-value proposal generator was comparing two different naming conventions and repeatedly regenerating blank stubs for workbooks that already existed.

Major refresh — PropertyType (PWLS 4.0) The well-log property reference list — the one nearly every well-log schema draws from — got its industry-standard refresh this milestone too. Numbers and detail in §6.
Technical detail — governance & supporting infrastructure

LOCAL lists are curated and maintained directly by the OSDU DD team; OPEN lists are maintained by the wider OSDU community and third parties can propose additions. Each new list above went through the full pipeline: an authoring workbook (ReferenceValues/Authoring/) → a manifest entry (ReferenceValues/Manifests/) → a published workbook (ReferenceValues/Published/).

Two existing lists also picked up content-only refreshes this milestone: SeismicGatherType (missing pre-stack gather configurations added) and the two patch-level bumps already covered in §1/§2 (RigType 1.0.1, VerticalMeasurementType 1.0.3).

Five additional workbooks were refreshed not as domain content but as the "wiring" that routes the 15 automatic schema upgrades in this release: PreferredSchemaVersion, ReferenceValueUpgradeLookUp, SchemaUpgradeChain, SchemaUpgradeSpecification, and UnitOfMeasureConfiguration — these tell the platform how to carry existing reference-data selections forward onto the new schema versions automatically.
